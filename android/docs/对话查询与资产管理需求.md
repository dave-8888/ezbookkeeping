# 安卓对话查询与资产管理需求

版本：v0.1（需求基线，核心规则已确认）  
日期：2026-09-13  
适用产品：`android/` 中的 financially_free 原生安卓对话记账应用。

> 后续状态：用户已确认按账户余额定义资产、区分资产/负债/净资产，默认不含隐藏且继承显式范围，更新为指定余额、明确时直接执行，以及今日支出合计加可展开明细。已按第 8 节顺序实现；下文保留需求分析时的建议与待确认记录，最终实现口径及验证见 [功能验证](finance-conversation-verification.md)。

## 1. 文档目的与依据

将用户提供的两张 App 对话截图整理为可评审的需求。截图中的消息是需求证据，不是本轮执行查询或修改真实资产的指令。本轮仅编写需求文档；尤其“第三条资产金额更新 6000元”不代表现在修改任何资产。

截图共包含 6 条去重后的用户表达，均收到 `no transaction information detected`。用户已明确这些表达都是真实需求。下文区分“已明确诉求”与“建议规则”；建议、统计口径和实施顺序需确认后再进入代码修改。

## 2. 问题与目标

当前用户希望通过对话完成查账、查看资产以及修改资产金额，但界面将这些请求统一反馈为未检测到交易信息，无法完成任务，也没有提供有效引导。

产品目标：在现有对话入口中区分记账、查询和资产更新，让用户可以先查看信息，再通过“第三条”等自然表达操作刚刚展示的对象。

## 3. 需求清单（6 项）

| 编号 | 用户原话 | 已明确诉求 | 建议结果形态 |
| --- | --- | --- | --- |
| R1 | 今日支出 | 查询今天的支出 | 当日支出合计、笔数；支持查看明细 |
| R2 | 今天的收入明细 | 查询今天每一笔收入 | 收入列表，并附合计与笔数 |
| R3 | 我现在的所有资产 | 查看当前资产情况 | 资产汇总，明确统计范围与币种 |
| R4 | 我现在的所有资产包含隐藏的 | 资产查询支持纳入隐藏项 | 包含隐藏项的汇总，并标明范围 |
| R5 | 列出我的所有资产列表 | 查看逐项资产清单 | 带序号、名称、金额、币种的列表 |
| R6 | 第三条资产金额更新 6000元 | 通过上文列表序号定位资产并更新金额 | 定位第 3 项，更新后反馈对象及金额变化 |

R3、R4 在两张截图中重复出现，计为同一需求。以下规则用于补齐可实现性，不能视为用户已经逐条确认。

## 4. 详细需求与建议规则

### R1：今日支出查询

- 识别“今日支出”“今天花了多少钱”等表达为查询，不创建交易。
- 建议先返回日期、支出合计和笔数；“今日支出”是否默认同时展开明细待确认。
- 建议按用户时区计算当天，范围为当日 00:00（含）至次日 00:00（不含），以交易发生时间筛选。
- 支出统计与账本已有口径一致，避免把转账或余额调整误计入消费；退款如何抵减需明确。
- 无记录时回复“今天暂无支出记录”，不能将无数据当作识别失败。

### R2：今日收入明细

- 识别“今天的收入明细”等表达，返回真实收入记录。
- 每笔建议展示时间、金额与币种、分类、收款账户、备注（有则展示），附当日收入合计和笔数。
- 建议按时间倒序排列；记录较多时分页或展开更多，合计必须涵盖完整查询范围。
- 无记录时回复“今天暂无收入记录”；日期规则与 R1 一致。

### R3：当前资产汇总

- 返回当前实际资产数据，而非从聊天历史推测金额。
- “资产”暂按资金账户及其当前余额理解，但是否还包含资产规划等其他对象，必须确认。
- 建议区分资产、负债、净资产，避免将账户余额简单相加后含糊称为“总资产”。是否需要这三项均展示待确认。
- 明确查询时间、纳入范围与币种。多币种在汇率口径明确前分币种展示，不直接相加。
- “所有资产”是否默认包含隐藏项待确认；结合用户另行强调“包含隐藏的”，建议普通查询默认不含隐藏项，并明确标注。

### R4：包含隐藏项的资产查询

- 显式说“包含隐藏的”时，查询范围须覆盖用户有权访问的隐藏资产；不能继续沿用仅可见项的数据源。
- 建议在结果中注明“含隐藏资产”，在明细中标记隐藏状态。
- 隐藏只影响展示范围，不应因查询而取消隐藏或修改资产设置。
- 汇总、明细采用相同范围；父子账户须避免重复统计。隐藏父账户下子账户如何纳入需统一。
- 是否将本次“包含隐藏”的范围延续到后续“列出所有资产”，需作为上下文规则确认。

### R5：资产列表

- 返回实际资产清单，每项建议展示：序号、名称、当前金额、币种及隐藏状态（适用时）。
- 序号从 1 开始，完整资产名称需可辨认。列表较长时允许展开或分页，并明确是否展示完整。
- 系统应保存本次展示序号与真实资产标识的对应关系，供后续引用使用。
- 列表排序和编号在该次结果中保持稳定；不得在用户说“第三条”时重新排序后选中另一项。
- 列表及汇总须说明同一统计范围。排序方式建议沿用现有账户顺序，待确认。

### R6：按上下文更新资产金额

- “第三条”关联当前对话中最近一次适用资产列表的第 3 项，绑定真实对象标识，不能只依赖名称或重新查询后的顺序。
- “更新 6000元”建议解释为将金额设置为 6000 元，而不是增加 6000 元；最终语义待确认。
- 没有适用列表、序号越界、目标已删除或引用不明确时，先要求用户明确对象，不猜测执行。
- “元”与目标账户币种不一致时需澄清，不直接换算或改币种。
- 执行前验证当前对象、权限及最新余额；若金额已被其他操作改变，应展示变化并重新明确操作意图。
- 成功后反馈资产名称、原金额、新金额、币种，并刷新相关资产结果；失败时说明失败，结果未知时不能声称成功或自动重复提交。
- 建议明确表达且对象唯一时直接更新并反馈；是否必须预览确认，以及是否提供撤销，由用户确定。
- 是否通过余额校准修改、是否生成调整流水及如何影响统计，属于待确认业务规则，不能误创建一笔 6000 元收入或支出。

## 5. 共性要求

1. **意图区分**：同一输入框支持现有收入/支出记账，以及新增查询、列举、资产更新。查询本身不得写入账目或修改余额。
2. **真实数据**：金额、笔数、资产对象来自当前登录用户的数据；模型负责理解表达，不编造查询结果或更新成功状态。
3. **上下文隔离**：资产引用按账号、服务器及对话隔离，不引用其他对话的“第三条”。重启后是否继续支持引用待确认；不能恢复时引导重新列出资产。
4. **范围可见**：日期、隐藏项范围、币种、分页状态及汇率口径应让用户看得懂。
5. **中文反馈**：区分无记录、无法理解、请求失败和更新结果未知。截图中的英文提示不能继续作为上述有效需求的统一回复。
6. **交互风格**：沿用原生对话入口，以简洁卡片、清晰金额层级与必要的展开操作呈现；遵循项目要求的简洁、一致、自然交互。
7. **现有能力保留**：正常收入/支出记账、字段补全、对话切换继续可用。

## 6. 验收场景草案

以下使用隔离测试数据，金额与账户名仅为示例，不代表用户真实资产。依赖待确认口径的断言，应在确认后定稿。

| 场景 | 输入或前提 | 预期 |
| --- | --- | --- |
| 今日支出 | 今日两笔支出 30 元、20 元，另有昨日支出 | 按已确认口径返回今日 50 元、2 笔，不包含昨日，不新增交易 |
| 今日收入 | 今日收入两笔，备注与账户不同 | 两笔均可查看，时间、金额、账户等与数据一致，合计正确 |
| 无数据 | 今日无收入 | 中文提示暂无收入，不报识别失败 |
| 普通资产 | 存在可见、隐藏账户 | 依已确认默认范围返回并标注，金额可核对 |
| 包含隐藏 | “我现在的所有资产包含隐藏的” | 隐藏项参与查询；隐藏状态不变，无父子重复统计 |
| 资产列表 | “列出我的所有资产列表” | 每项有可引用的稳定序号和名称、金额、币种 |
| 序号更新 | 最近列表第 3 项为人民币账户 A，原余额 5000 元 | 按确认流程将 A 设为 6000 元；其他对象不变；回读数据一致 |
| 引用失效 | 无上文列表、只有 2 项、切换对话或目标已删除 | 不修改数据，明确提示重新指定对象 |
| 列表变化 | 展示后其他账户排序变化 | 仍定位原展示的第 3 项，不误改新排序中的第 3 项 |
| 多币种 | 列表包含人民币和美元 | 明确币种；无有效汇率口径时不输出混合总额 |
| 更新异常 | 请求失败或响应丢失 | 区分失败与结果未知，不虚报成功、不自动重复写入 |
| 原有记账 | “午饭花了 30 元” | 继续按原有记账/补全流程处理 |

## 7. 现状核对与实现约束

本节仅记录仓库观察，不作为已完成的实现设计。

- `android/README.md`：安卓当前以单笔收入、支出识别和自动记账为主要能力，使用原生对话入口。
- `android/app/src/main/java/net/ezbookkeeping/chat/ChatViewModel.kt` 的 `send()`：发送后直接调用 `recognize_transaction_text.json`，随后进入交易补全或保存。这与截图中查询也收到交易识别错误的现象一致，但尚未核验真实设备请求日志。
- `android/app/src/main/java/net/ezbookkeeping/chat/Api.kt` 的 `catalog()`：请求 `accounts/list.json?visible_only=true`，并过滤隐藏项；当前目录数据不能直接满足包含隐藏资产的需求。
- `pkg/api/account_balances.go`：已有按账户标识设置余额的处理逻辑，可作为 R6 的复用候选；账户余额是否等同于用户所说的“资产金额”及其流水影响，需进一步确认。

实现前需核对交易查询、账户及余额接口的完整性和统计口径。不能仅靠修改模型提示词就认为需求已满足。

## 8. 建议执行顺序（待用户确认）

业务需求共 6 项，建议分 4 步推进：

1. 确认资产定义、统计范围、金额更新语义和交互方式，补齐意图区分及中文反馈的设计。
2. 完成 R1、R2：今日支出和收入明细，验证查询与记账互不混淆。
3. 完成 R3、R4、R5：资产汇总、隐藏范围、稳定编号列表，共用一致的数据口径。
4. 完成 R6：基于列表上下文定位和更新金额，验证引用正确性与写入结果，再进行整体回归。

理由：资产更新依赖正确的数据范围与稳定列表上下文，应在查询和列表完成后实现。本文不代表已获准按该顺序开始开发。

## 9. 待确认问题

| 问题 | 建议默认方案（尚未确认） |
| --- | --- |
| “资产”指资金账户余额，还是也包括资产规划等其他对象？ | 先按账户余额；汇总明确区分资产、负债和净资产 |
| “所有资产”是否默认包含隐藏项？后续列表是否继承“包含隐藏”的条件？ | 默认不含隐藏；同一连续查询中继承显式条件，并在结果标注 |
| “第三条资产金额更新 6000元”是设为 6000 元还是增加 6000 元？ | 设为 6000 元；增加金额使用“增加”等明确表达 |
| 明确更新请求是否直接执行？是否需要确认或撤销？ | 对象、金额唯一明确时直接执行并反馈；含糊时澄清 |
| 更新采用余额校准还是生成调整流水？ | 优先复用现有余额修改业务规则，确认对历史流水及统计的影响后定稿 |
| 今日支出默认显示合计还是全部明细？今天采用哪个时区？ | 合计及笔数，明细可展开；沿用账本既有时区口径 |
| 查询是否含隐藏账户的交易？多币种如何汇总，退款如何计入？ | 与账本现有统计保持一致并明确范围；汇率不明确时分币种展示 |
| 是否认可上述 4 步实施顺序？ | 确认规则 → 收支查询 → 资产查询与列表 → 上下文更新 |

## 10. 当前范围之外

截图没有提出恢复独立资产页面、新建或删除资产、批量更新、投资估值、资产预测、跨对话记忆等要求，本稿不将其列为必做范围。它们如有需要应单独补充确认。
